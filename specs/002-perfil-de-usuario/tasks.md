## Hallazgos preservados de T1

- `public.user_profiles` local coincide con la baseline: ID ligado a Auth, campos de perfil nullable, rol por defecto `user_restricted` y trigger de `updated_at`.
- Las policies de escritura locales exigen `id = auth.uid()`, pero `user_profiles select anon` y `user_profiles select own` permiten `SELECT` con `true`; los grants de `anon`/`authenticated` son amplios.
- `storage.objects` y `storage.buckets` tienen RLS, pero no hay policies y no existe `avatars`. No se inspeccionaron filas ni objetos.
- El formulario guarda URL pública, extrae cualquier sufijo tras `/avatars/` y borra antes de persistir la nueva referencia; la navegación acepta URL absoluta y lista la carpeta del usuario si falta referencia.
- La API GET existente deriva identidad, pero consulta mediante service-role; las escrituras actuales se hacen desde navegador. No existen rutas server-side de escritura/email/avatar.
- La inspección fue solo contra `supabase_db_menu-planner-wit-ai`, en transacciones de catálogo `READ ONLY`; no hubo link, remoto, lectura de usuarios/objetos ni cambios en DB/Storage.
