# Spec 001 — Autenticación y sesión
## Contexto y objetivo
Especificar el comportamiento esperado de autenticación para que quienes usan la aplicación puedan crear una cuenta, iniciar y cerrar sesión y recuperar el acceso mediante una nueva contraseña. La cuenta y la sesión permiten acceder a las funcionalidades personales de la aplicación. Los requisitos expresan el resultado esperado del producto; la evidencia de implementación se documenta por separado y cualquier discrepancia constituye un gap, no una razón para rebajar el requisito.
## Usuarios / actores
- Personas que crean una cuenta o acceden a una cuenta existente.
- Usuario autenticado que cierra su sesión.
- Usuario que usa un enlace de recuperación recibido para establecer una nueva contraseña.
- Proveedor de autenticación, que procesa las operaciones y los enlaces de recuperación de contraseña cubiertos por esta especificación.
## Historias de usuario
- H1: Como visitante quiero crear una cuenta para acceder a la aplicación.
- H2: Como usuario registrado quiero iniciar sesión para utilizar mi cuenta.
- H3: Como usuario autenticado quiero cerrar sesión para terminar mi acceso.
- H4: Como usuario con un enlace de recuperación quiero establecer una nueva contraseña para recuperar el acceso.
## Requisitos funcionales (criterios de aceptación en EARS)
- RF-1: CUANDO una persona envía correo electrónico y contraseña mediante el formulario de registro, EL SISTEMA solicita el registro; SI el proveedor devuelve un error, EL SISTEMA muestra el mensaje de error recibido; SI no devuelve error, EL SISTEMA muestra una confirmación que indica revisar el correo para confirmar la cuenta.
- RF-2: CUANDO se completa el registro, EL SISTEMA crea un perfil asociado a la cuenta con rol predeterminado `user_restricted`.
- RF-3: CUANDO una persona envía correo electrónico y contraseña para iniciar sesión, EL SISTEMA solicita la autenticación; SI esta falla, EL SISTEMA muestra el mensaje de error recibido; SI tiene éxito, EL SISTEMA muestra «¡Inicio de sesión exitoso!» y deja que el flujo de autenticación determine la navegación posterior.
- RF-4: MIENTRAS el proveedor mantiene una sesión autenticada, EL SISTEMA muestra la identidad del usuario mediante las áreas de la aplicación que consumen la sesión.
- RF-5: CUANDO un usuario solicita cerrar sesión, EL SISTEMA solicita terminar la sesión y, cuando se completa el cierre, elimina el usuario y el perfil del estado de interfaz y dirige al usuario a `/login`.
- RF-6: CUANDO el callback de recuperación recibe un enlace válido con `code` o `token_hash`, EL SISTEMA procesa el enlace y dirige al usuario a la pantalla para establecer una nueva contraseña. Este requisito se limita a recuperación de contraseña.
- RF-7: CUANDO el usuario envía una nueva contraseña y su confirmación que no coinciden, EL SISTEMA informa de que deben coincidir y no solicita la actualización de la contraseña.
- RF-8: CUANDO el usuario envía una nueva contraseña de menos de seis caracteres, EL SISTEMA informa de que debe tener al menos seis caracteres y no solicita la actualización de la contraseña.
- RF-9: CUANDO el proveedor acepta la nueva contraseña, EL SISTEMA muestra una confirmación de actualización y dirige al usuario a la página principal exactamente 2 segundos después.
- RF-10: SI el callback de recuperación recibe un error de expiración OTP, ENTONCES EL SISTEMA dirige al usuario a `/login` e informa de que el enlace expiró y debe solicitar uno nuevo.
- RF-11: SI el callback de recuperación falla durante cualquier vía de procesamiento, ENTONCES EL SISTEMA dirige al usuario a `/login` e informa del error y de que solicite un enlace nuevo.
- RF-12: SI el usuario abre la pantalla de nueva contraseña sin una sesión, ENTONCES EL SISTEMA dirige al usuario a `/login`.
## Requisitos no funcionales
- La sesión se mantiene mediante cookies y es compartida por el navegador y los procesos de servidor de la aplicación.
- La interfaz o el middleware no constituyen por sí solos autorización; las operaciones protegidas deben comprobar permisos en servidor según las reglas generales existentes.
- No se especifican niveles de disponibilidad, rendimiento ni políticas de contraseña adicionales a las observadas (mínimo de seis caracteres al establecer una nueva contraseña).
## Casos límite
- Ante un error del proveedor durante el registro, EL SISTEMA muestra el mensaje devuelto por Supabase. El mensaje específico que Supabase devuelve para un correo duplicado queda [NECESITA ACLARACIÓN].
- Un inicio de sesión con error muestra el error comunicado por el proveedor.
- Una confirmación de correo puede requerirse tras el registro; no se considera garantizado que el usuario quede autenticado de inmediato.
- Un enlace de recuperación vencido conduce a inicio de sesión con aviso de expiración y solicitud de pedir otro enlace.
- Si no existe una sesión al abrir la pantalla de nueva contraseña, el flujo actual dirige a inicio de sesión.
- La spec cubre únicamente el procesamiento de callbacks de recuperación de contraseña y la actualización de contraseña. Otros callbacks de autenticación, incluidos confirmación/signup con `code` o `token_hash`, quedan fuera de esta spec y de RF-6. Solicitar el envío del correo queda fuera del alcance confirmado.
- [NECESITA ACLARACIÓN] No se ha confirmado si existe fuera del repo una interfaz para solicitar el correo de recuperación.
- [NECESITA ACLARACIÓN] No se ha confirmado cuál es el mensaje que devuelve Supabase en el caso concreto de correo duplicado.
- La creación efectiva del perfil con rol `user_restricted` está verificada en Supabase local durante T9. Esta comprobación local no acredita comportamiento remoto; los scripts históricos por sí solos tampoco prueban despliegue.
- Al cambiar la contraseña, la confirmación debe coincidir con la nueva contraseña y esta debe tener al menos seis caracteres; si cualquiera de estas condiciones falla, no se solicita la actualización.
## Fuera de alcance
- Consulta o edición posterior del perfil de usuario; corresponde a la spec 002.
- Solicitud del correo de recuperación.
- Gestión de roles, permisos y autorización de funcionalidades, salvo las reglas generales que deben seguirse al consumir una sesión.
- Cambios de proveedor, arquitectura, almacenamiento o configuración de autenticación.
- Comportamientos de invitaciones u otros tipos de callback que no forman parte de las decisiones de alcance aprobadas para esta spec.
## Criterios de finalización
- Los RF describen el comportamiento esperado aprobado, no necesariamente garantizado por la implementación actual; toda discrepancia se registra como gap. RF-2 fija `user_restricted` como rol predeterminado para un usuario nuevo.
- Las dudas sobre la disponibilidad fuera del repo de una interfaz para solicitar el correo de recuperación y el mensaje específico del caso de correo duplicado permanecen en «Dudas abiertas». T9 verificó localmente el signup y la creación del perfil con rol `user_restricted`; la captura de migraciones remotas no evidencia comportamiento funcional remoto. La UI, el flujo de recuperación y los tests correspondientes siguen pendientes o parciales según la evidencia T9. En el intento UI más reciente el signup falló con `Failed to fetch`, sin petición observada al Supabase local; esto no revoca la prueba previa de signup/perfil a nivel de proveedor ni demuestra un registro/perfil nuevo desde UI.
- No se interpreta la presencia de scripts SQL como prueba de que estén desplegados en ningún entorno.
## Dudas abiertas
- [NECESITA ACLARACIÓN] ¿Qué respuesta visible específica se requiere para el caso concreto de correo duplicado? El código muestra el mensaje devuelto por Supabase.
- [NECESITA ACLARACIÓN] ¿Existe fuera del repo una interfaz para solicitar el correo de recuperación? La solicitud queda fuera del alcance confirmado.

## Evidencia retrospectiva — RF-1 y RF-2

### RF-1: flujo de registro observado

En `components/auth/login-form.tsx`, el botón «Crear Cuenta» invoca `handleSignUp`, que evita el envío del formulario, activa el estado de carga y limpia los mensajes previos. Solicita `supabase.auth.signUp({ email, password })` con los valores actuales del formulario. Si Supabase devuelve un error, se muestra `error.message`; si la llamada lanza una excepción, se muestra «Error inesperado al registrarse». Si no devuelve error, se muestra «¡Registro exitoso! Revisa tu email para confirmar tu cuenta.» El estado de carga termina en todos los casos. El componente no implementa un mensaje específico para correo duplicado; se conserva como duda abierta el resultado concreto que devuelva Supabase.

### RF-2: definición de perfil en scripts

Los scripts `scripts/create-user-profile-trigger.sql` y `scripts/fix-user-profile-trigger.sql` definen una función trigger `public.handle_new_user()` y un trigger `on_auth_user_created` sobre `auth.users`; la función inserta una fila en `public.user_profiles` usando el id/correo y metadatos disponibles. Las versiones difieren, entre otros detalles, en el rol asignado por defecto (`user_full` frente a `user_restricted`) y en el manejo/log de errores; ambas capturan errores de inserción y permiten que continúe el registro de usuario. `scripts/check-and-create-user-profile-trigger.sql` contiene consultas de inspección, no demuestra que el trigger exista en un entorno. `scripts/create-missing-user-profile.sql` define una inserción manual para un usuario concreto, no el flujo general.

Esta evidencia describe únicamente definiciones versionadas en el repositorio. Conforme a `docs/DATABASE.md` (sección «Gestión de cambios»), la presencia de SQL no demuestra su ejecución ni el estado del trigger en desarrollo, preproducción o producción. La validación inicial no ejecutó scripts ni consultó Supabase. Posteriormente, el usuario informó que aplica y registra manualmente siempre las migraciones remotas; además, aportó una captura de `supabase migration list --linked` donde Remote muestra `20261024000000` (baseline) y `20261024010000` (`install_user_profile_trigger`) como aplicadas. Esto acredita el estado listado en la captura y la operación manual declarada por el usuario, no una ejecución o intervención del agente en remoto. La creación efectiva del perfil queda verificada en local según T9; no se infiere de la captura remota ningún comportamiento funcional adicional.

## Evidencia retrospectiva — RF-3 y RF-4

### RF-3: inicio de sesión observado

En `components/auth/login-form.tsx`, el envío del formulario ejecuta `supabase.auth.signInWithPassword` con el correo recortado y la contraseña; mientras espera, muestra «Cargando...», desactiva los botones y limpia mensajes previos. Si Supabase devuelve error se muestra `error.message`; si lanza excepción se muestra su mensaje cuando es `Error` o «Error inesperado al iniciar sesión». Sin error se muestra «¡Inicio de sesión exitoso!». El formulario declara que no navega por sí mismo. En `app/login/page.tsx`, cuando el contexto termina de cargar y contiene usuario, se reemplaza la ruta por el parámetro `redirect`, o `/recipes` si no existe. La confirmación visible no acredita que la navegación haya ocurrido en ejecución real.

**Estado RF-3: respaldado estáticamente por implementación; comportamiento funcional no verificado.** `tests/unit/components/login-redirect.test.tsx` contiene casos de prueba simulados de inicio/redirect, pero el test incluye expectativas y controles de formulario que no corresponden a la implementación actual (`LoginForm` exporta nombre y no tiene los modos referidos por dicho archivo). No se ejecutó Jest ni se considera ese archivo evidencia funcional válida. No se usaron credenciales ni servicios remotos.

### RF-4: identidad y sesión observadas

`components/auth/auth-provider.tsx` inicializa `user` desde `supabase.auth.getSession()` y escucha `onAuthStateChange`; con una sesión coloca su usuario en contexto y solicita el perfil a `/api/profile`, reintentando la carga si falta. Sin sesión limpia usuario y perfil. La navegación y numerosos consumidores usan `useAuth`; por ejemplo, `components/simple-navigation.tsx`, `app/page.tsx`, `components/recipes-page-client.tsx` y `components/role-guard.tsx`. El contexto expone tanto `user` como `profile`, pero el perfil puede ser `null` ante respuesta ausente/fallo, independientemente de que haya usuario.

La ruta `/api/profile` resuelve la identidad desde bearer token validado o desde cookies y consulta el perfil asociado al id del usuario resuelto. El cliente de navegador de `lib/supabase/client.ts` usa `createBrowserClient` de `@supabase/ssr`; el cliente de servidor de `lib/supabase/server.ts` adapta lectura/escritura de cookies. `app/recipes/page.tsx` obtiene `cookies()` y pasa el almacén al cliente de servidor. `middleware.ts` refresca/sincroniza cookies mediante `getSession`; su comentario y `docs/AUTH.md` aclaran que no reemplaza autorización en servidor. También existe `components/providers/session-wrapper.tsx` con estado alternativo de sesión de usuario, pero no se deduce de su existencia que cada consumidor visible incluya la identidad.

**Estado RF-4: patrón de sesión/consumo respaldado estáticamente; identidad mostrada condicionalmente por consumidores y perfil no garantizado. Comportamiento funcional no verificado.** La documentación normativa (`docs/AUTH.md`, `docs/ARCHITECTURE.md`, `docs/DATABASE.md`) concuerda en cookies compartidas cliente/servidor y en no inferir autorización de middleware/UI. No se consultó ningún proyecto Supabase ni se comprobaron cookies o identidad en una sesión real.

## Evidencia retrospectiva — RF-5

### RF-5: cierre de sesión observado

La navegación utilizada por `app/page.tsx`, `app/weekly-menu/[week]/page.tsx`, `app/seasonal-products/page.tsx` y `app/freezer/page.tsx` es `components/simple-navigation.tsx`, que obtiene `signOut` de `components/auth/auth-provider.tsx`. Sus acciones de cierre en escritorio y móvil invocan ese helper (la variante móvil además cierra el menú y ambas limpian el avatar presentado). El helper del proveedor limpia inmediatamente `user` y `profile` y pone `loading` a falso, antes de completar peticiones; luego solicita `POST /api/auth/sign-out`, llama también a `supabase.auth.signOut()`, limpia claves `sb-` de `localStorage` y ejecuta `router.replace("/login")` seguido de `router.refresh()`. En caso de excepción de navegación usa `window.location.assign("/login")`. Los errores de ambas solicitudes de cierre se ignoran. La ruta API, por su lado, ejecuta `supabase.auth.signOut()` usando cookies y responde error HTTP si falla.

**Discrepancia/límite de RF-5:** la limpieza del estado local y el destino `/login` están codificados, pero el helper no condiciona navegación/limpieza a que el cierre del proveedor haya tenido éxito; además no propaga ni muestra fallos de cierre. Por tanto, la evidencia respalda la solicitud y los efectos locales previstos, no que el proveedor haya terminado efectivamente la sesión en caso de error. No se verificó invalidación de cookies/sesión en ejecución. Existe además `components/navigation.tsx`, cuyo handler independiente llama `supabase.auth.signOut()` y dirige a `/` sin limpiar explícitamente el contexto; no se encontraron usos de ese componente bajo `app/`, mientras que sí hay usos de `SimpleNavigation`. Se registra como implementación alternativa no consumida por las páginas localizadas, no como comportamiento del flujo de navegación actualmente localizado.

**Gap RF-5:** el comportamiento esperado es que el cierre de sesión se complete antes de eliminar el usuario/perfil y navegar a `/login`. La implementación limpia y navega sin condicionar ese resultado al éxito del proveedor y no informa de errores. El logout probado en proveedor Auth local durante T9 no verifica el comportamiento de aplicación exigido por RF-5; UI, estado y navegación siguen sin validación funcional.

**Estado del gap RF-5 (2026-11-15):** la descripción anterior es la evidencia retrospectiva de T1–T8 y el gap quedó confirmado funcionalmente el 2026-11-11 (el Auth local nunca recibió `/logout` y los refresh tokens siguieron activos). **El gap está cerrado en código desde T10:** `components/auth/auth-provider.tsx` delega en `runSignOut` de `lib/auth-flow/auth-flow.js`, que revoca primero en servidor y sólo limpia estado y navega a `/login` si el cierre se confirma; `app/api/auth/sign-out/route.ts` usa el cliente de cookies de `lib/supabase/server.ts` con `signOut({ scope: "local" })` y responde 500 ante error. `components/navigation.tsx` sigue existiendo con su handler alternativo y sigue sin ser consumido por ninguna página de `app/`. **Revalidado funcionalmente el 2026-11-15:** el Auth local recibe `POST /logout` 204 y el usuario queda sin sesiones ni refresh tokens vivos.

## Evidencia retrospectiva — RF-6, RF-10 y RF-11

### RF-6: entradas y éxito del callback

En `app/auth/callback/route.ts` el handler GET lee `code`, `token_hash` y `type`. Para recovery, con `token_hash` invoca `verifyOtp`; con `code` usa `exchangeCodeForSession`. Si no hay error y el tipo es recovery, redirige a `/auth/reset-password`. Las demás ramas `code`/`token_hash` (por ejemplo confirmación/signup) están fuera de esta spec y de RF-6.

**Gap/límite de RF-6:** el adaptador de cookies crea un `NextResponse` y escribe cookies en `setAll`, pero el handler devuelve redirects nuevos en sus ramas de éxito y no devuelve explícitamente ese response. La inspección estática no acredita que las cookies de sesión queden incorporadas al redirect respondido. No se verificó sesión funcional.

### RF-10: expiración OTP

Antes de procesar credenciales, si `error=access_denied`, `error_code=otp_expired` y `type=recovery`, dirige a `/login?error=recovery_expired&message=El enlace de recuperación ha expirado. Solicita uno nuevo.` La rama estática coincide con RF-10, pero el comportamiento esperado no se ha validado funcionalmente.

### RF-11: fallos de procesamiento

Si el proveedor devuelve `authResult.error` en recovery, dirige a `/login` con `error=recovery_error` y el mensaje «Error en la recuperación de contraseña. Solicita un nuevo enlace.» Si la operación lanza una excepción, el `catch` dirige a `/login?error=unexpected_error&error_description=...` usando el mensaje de excepción, sin garantizar aviso de solicitar otro enlace. Los parámetros `error` de entrada se reenvían a `/login` como `error`, `error_code` y `error_description`, sin aviso específico de recovery. Si faltan `code` y `token_hash`, la ruta es `/login?error=missing_code&message=No se encontró el código de autenticación`.

**Gap RF-10:** el resultado esperado no se validó funcionalmente. **Gap RF-11:** sólo el error devuelto por el proveedor durante recovery incluye explícitamente el aviso requerido; excepciones y errores genéricos no garantizan ese aviso, aunque dirigen a `/login`. El mensaje de excepción se coloca en `error_description`; esta revisión no acredita cómo lo presenta la interfaz.

**Estado RF-6/RF-10/RF-11:** gaps de implementación/evidencia según lo descrito; callback y recuperación no probados funcionalmente. El gate SMTP local está confirmado: el host efectivo es `supabase_inbucket_menu-planner-wit-ai`, puerto `1025`. No se envió correo ni se solicitó recovery; estos RF siguen pendientes sin captura/evidencia. No se probaron enlaces reales, cuentas remotas ni producción; tampoco se ejecutó la utilidad CORS. Los callbacks no recovery están fuera de esta spec.

**Estado RF-6/RF-10/RF-11 (2026-11-15):** lo anterior es la evidencia retrospectiva de T1–T8 y describe una implementación ya sustituida. **Los gaps de RF-6 y RF-11 están cerrados en código desde T10**, y RF-10 se reimplementó sobre la misma clasificación: el callback devuelve la propia respuesta de redirección que lleva las cookies, y todas sus vías de fallo pasan por un único `failureRedirect` que propaga sólo un código público (`recovery_expired`, `recovery_error`, `auth_error`); el texto lo resuelve la aplicación con `getCallbackNotice` y lo muestra `components/auth/login-form.tsx`, de modo que la URL ya no transporta mensajes (`message` y `error_description` dejaron de renderizarse). **Validados funcionalmente el 2026-11-15** contra el buzón local: callback con `token_hash` real que entrega una sesión utilizable, aviso de enlace expirado y aviso de error por tres vías, sin que la URL pueda inyectar texto. Los callbacks no recovery siguen fuera de esta spec.

## Evidencia retrospectiva — RF-7, RF-8, RF-9 y RF-12

### RF-7 y RF-8: validación de contraseña

En `app/auth/reset-password/page.tsx`, `handlePasswordUpdate` limpia avisos anteriores y activa `loading`, después compara la contraseña y su confirmación. Si no coinciden, muestra «Las contraseñas no coinciden», desactiva carga y retorna sin llamar a Supabase. En caso contrario comprueba `password.length < 6`; si se cumple, muestra «La contraseña debe tener al menos 6 caracteres», desactiva carga y retorna sin actualización. La comprobación de longitud usa unidades UTF-16 de JavaScript; no se documenta otra política de composición ni normalización. Ambos campos también declaran `required` y `minLength={6}` en HTML, aunque las comprobaciones del handler son la evidencia de que no se llama al proveedor.

### RF-12: sesión requerida

Al montar, un efecto solicita `supabase.auth.getSession()` y, si no recibe sesión, ejecuta `router.push("/login")`. No se representa estado de comprobación ni se impide explícitamente enviar el formulario mientras la consulta está pendiente; el handler no vuelve a verificar sesión antes de `updateUser`. Por tanto, la redirección sin sesión está codificada de forma asíncrona en cliente, pero no constituye una barrera de autorización/servidor ni acredita que la actualización esté impedida durante la carrera entre montaje y comprobación. Fallos/excepciones de `getSession` tampoco tienen manejo visible en ese efecto. No se probó una sesión real.

### RF-9: actualización aceptada y retardo

Tras superar las validaciones, el componente llama `supabase.auth.updateUser({ password })`. Si el resultado contiene error, lo lanza y muestra `error.message` o, si no existe, «Error al actualizar la contraseña»; no programa navegación. Si no hay error, muestra «¡Contraseña actualizada exitosamente! Redirigiendo...» y programa `router.push("/")` mediante `setTimeout(..., 2000)`. El `finally` termina `loading`. La cifra es un retardo solicitado de 2000 ms desde la programación; el navegador/event loop puede ejecutarlo más tarde, de modo que el código no garantiza tiempo real exacto.

Para evaluar RF-9 se fija explícitamente como referencia temporal **hoy: 2026-10-24 (hora del entorno indicada al inicio de la tarea)**. El código inspeccionado no contiene fechas absolutas ni una fecha límite; el retardo se mide desde cada actualización aceptada y, por ello, hoy no altera el resultado. No se introdujo una función temporal de evaluación ni se usó reloj implícito como criterio.

**Estado RF-7–RF-9/RF-12: comportamiento descrito respaldado por inspección estática de `app/auth/reset-password/page.tsx`; no se ejecutó autenticación funcional ni se llamó a Supabase.** Casos límite documentados: inputs vacíos están sujetos a `required`; contraseñas Unicode se miden por `String.length`; error devuelto/excepción de actualización muestra mensaje; falla de consulta de sesión carece de tratamiento visible; la sesión puede cambiar entre comprobación y actualización; no hay cancelación del temporizador al desmontar; y los 2000 ms son retardo programado, no garantía de navegación exacta en tiempo real.

## Evidencia retrospectiva — revisión transversal de seguridad (T6)

### Cookies y límites cliente/servidor (RF-4, RF-5, RF-6, RF-12; NFR)

La implementación usa `createBrowserClient` de `@supabase/ssr` en `lib/supabase/client.ts` con URL y clave anon públicas; `lib/supabase/server.ts` crea cliente de servidor utilizando cookies y las mismas credenciales públicas. `docs/AUTH.md` describe este esquema compartido y `app/recipes/page.tsx` sigue el patrón de esperar `cookies()` y pasar el almacén al cliente server. `middleware.ts` llama `getSession()` y sincroniza cookies de respuesta para refrescar la sesión.

**Límite de autorización:** el middleware sólo sincroniza/refresca cookies; no comprueba permisos ni constituye autorización por sí mismo. Cada página/ruta/servicio protegido debe validar en servidor sesión, identidad, propiedad/rol y acción permitida. La presencia de una cookie, la redirección cliente o la identidad del contexto no bastan para autorizar una operación.

La separación está documentada y mantenida en los puntos revisados, pero es por convención, no completamente forzada: `lib/auth.ts` y `lib/supabase/server.ts` indican uso exclusivo de servidor, y no incluyen import `server-only`. `lib/auth-client.ts` es el subconjunto cliente de utilidades de roles/permisos; su resultado sólo puede orientar interfaz, no sustituir decisión server-side. `lib/auth.ts` y `lib/auth-client.ts` duplican helpers y requieren coherencia al cambiar roles. Esto es evidencia estática de los módulos inspeccionados, no auditoría de todos los imports del bundle.

### Errores visibles y datos sensibles

Los formularios de inicio/registro muestran mensajes del proveedor (o mensajes genéricos ante excepciones); la pantalla de restablecimiento presenta errores de validación y el mensaje de error de `updateUser`.
